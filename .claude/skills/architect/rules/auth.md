# Architecture Rules — auth

Доступ: токены в покое, OAuth брокера, bearer bot → backend. Индекс — `.claude/skills/architect/SKILL.md` → Architecture Rules.

### Rule 11
11. **Токены в покое** — AES-256-GCM, AAD = `keyId|accountId|field` с запретом `|` в частях, `token_key_id` для ротации (`packages/db/src/crypto.ts`, `broker-accounts.ts`).

### Rule 12
12. **OAuth.** State хранится только хешем и одноразов через CAS по `used_at` (`oauth-states.ts`, `oauth-ops.ts`); аккаунт, привязанный через OAuth-callback (`linkBrokerAccount(…, activate: false)`), начинает с `pending` и активируется только подтверждением в боте (default колонки, миграция 0005); вход по почте (#162) — единственный путь с `activate: true`: аккаунт сразу `active`, стартовый пакет в той же транзакции; бот предлагает только вход по почте (#314): под приветствием и в `/account` — одна кнопка `connect`, старая кнопка `oauth` только снимает клавиатуру своего сообщения, без вызова backend (`bot.test.ts`), `POST /auth/binodex/start` удалён — 404 с bearer и без, state не создаётся (`routes.db.test.ts`); callback, подтверждение и refresh работают для state и привязок, созданных раньше; заблокированный пользователь не доходит до брокера (`oauth-ops.ts` → `user_blocked`); токен брокера не выдаётся аккаунту заблокированного пользователя: `lockAccountForRefresh` блокирует строку аккаунта (`for no key update`, `users` не блокируется) и читает `users.status` отдельным statement'ом (`readUserStatus`) — блокировка, закоммиченная, пока statement ждал lock, видна; на пути обмена `refreshUnderLock` читает статус ещё раз после сохранения ротированной пары и при `blocked` токен не выдаёт (`user_blocked`, пара сохранена, revocation нет) (`token-service.db.test.ts` B1, B2, #239); остаточное окно — от последнего чтения до последнего обращения к брокеру с выданным токеном, по вызывающим — `docs/binodex-oauth.md` → The window after the last read; блокировка, закоммиченная в нём, выданный токен не останавливает (stated); callback принимает code+state только с подписанным Telegram `initData` владельца state — подпись и возраст проверяются до запроса в БД (`apps/backend/src/auth/telegram-init-data.ts`), id сравнивается с `oauth_states.telegram_user_id` из строки CAS до обмена кода (`apps/backend/src/auth/routes.ts`, #113); refresh: `revoked` проверяется до истечения, ровно одна попытка обмена, не retry; сбой, после которого пара могла быть потрачена (таймаут, обрыв, 5xx, 4xx кроме 401 и 429, 2xx вне контракта), → revocation `refresh_outcome_unknown`, 401 → `refresh_invalid_grant`; 429 (`BrokerOAuthErrorCode.RateLimited`, `classify` в `oauth-client.ts`) — отказ до действия: пара и строка не трогаются, ответ `refresh_rate_limited` (409 на роуте), повтор — решение вызывающего (`token-service.db.test.ts` T1–T3, `oauth-client.test.ts` → status map); что 429 брокера приходит до чтения токена — stated (`docs/binodex-oauth.md` → Live check: a 429) (`apps/backend/src/auth/token-service.ts`, `docs/binodex-oauth.md` → Refresh). Обмен — по действию пользователя и при сверке intent'а с неизвестным исходом (#90): `POST /trading/accounts/:id/access-token` (internal bearer) вызывает `ensureFreshAccessToken` с `mayRefresh` из тела (обязательное поле); REST-реконсилер worker'а передаёт `true` (решение владельца 2026-10-06; принятый риск — revocation при сбое брокера только у аккаунтов с открытой сверкой), касса `POST /deposit/widget-session` (#11) — `true` (действие пользователя), `POST /deposit/credited` (#112) — `true` через `balance.refresh` с `requested: true` (действие пользователя, `credited.db.test.ts` K5), CLI `deposit-probe` — `false`; catch-up расчёта, фоновый цикл баланса и ответ view завершённой сессии (`GET /trading/sessions/:id`, `POST …/:id/stop`, #337, `session-routes.db.test.ts` G5) — `false`, и под блокировкой строки истекающий токен при `false` возвращает `refresh_needed` без обмена и без revocation по возрасту (`token-service.db.test.ts`, `apps/backend/src/trading/access-token.test.ts`); отбор кандидатов с валидным токеном (`listBalanceRefreshCandidates`, `accessSkewMs`) — оптимизация, не гарантия. Таймер обменивает только токен служебного аккаунта (#391, docs/service-accounts.md): keeper backend'а (`apps/backend/src/broker/service-accounts.ts`) и источник свечей (#404, Rule 41: старт клиента на аккаунте с истёкшим или отвергнутым брокером токеном) вызывают `ensureFreshAccessToken` с `serviceOnly: true`, отметка `service_since` проверяется под блокировкой строки после проверок статуса, иная строка — `not_service` без расшифровки и обмена и до ветки `refusedToken` (`token-service.db.test.ts` V1, V6, `service-accounts.db.test.ts` K2); правила сбоя обмена — общие (одна попытка, 429 без отзыва, остальное — revocation). Отказ брокера по выданному токену (#281): сокетные `token_expired`/`auth_failed` у менеджера сессий (`mayRefresh: false`), REST 401 у executor'а (`mayRefresh` по умолчанию `true`, отчёт не ожидается — гонка с дедлайном процессора не должна превращать `rejected` в `unknown`), REST-реконсилера (`true`), catch-up'а (`false`), backend-реконсилера баланса (`false`) и кассы (#11, `false`, `deposit/widget-session.ts` → `reportRefused`, `deposit/routes.db.test.ts` D5) передают в `ensureFreshAccessToken`/`POST /trading/accounts/:id/access-token` `refusedToken` — sha256 (`hashToken`) отвергнутого токена (`reportRefusedToken` в `apps/trading-worker/src/broker/access-token.ts`, `reportRefused` в `balance-reconciler.ts`); `refreshUnderLock` под блокировкой строки, после всех проверок статуса, сверяет его с сохранённым access-токеном и при совпадении пишет `access_token_expires_at = now() - 1 day` (`markAccessTokenExpired`, `oauth-ops.ts`; сутки назад — чтобы метку видели и часы процесса, отстающие от часов БД), после чего решение идёт как для просроченного токена — таймер обычных аккаунтов по-прежнему не обменивает; несовпадение ничего не пишет (`token-service.db.test.ts` T1–T5; по вызывающим — `session-manager.test.ts` U6/U6c/U7, `trade-command-executor.test.ts` R1/R6/R7, `rest-reconciler.test.ts`, `settlement-catchup.db.test.ts`, `balance-reconciler.db.test.ts`); 429/5xx/`unavailable` отчёта не дают. Пустой или пробельный `user.email` брокера становится `null` в `toOAuthTokens` (`addressOrNull`, `packages/shared/src/oauth.ts`); та же функция — в `toBrokerAccountView`, `toLinkedAccountView`, `toUserStartView` для строк, записанных раньше (#214); CHECK на колонке нет — для будущего писателя правило stated.

### Rule 13
13. **bot → backend:** общий bearer, сравнение за постоянное время (`timingSafeEqual` в `apps/backend/src/auth/internal.ts`); внутренний API полностью доверенный; чтения не скоупятся по пользователю, кроме `GET /trading/intents/:id` (#127): id intent'а приходит из callback data кнопки бота, поэтому чтение требует `telegramUserId` и фильтрует по владельцу (`getTradeIntentView`, `routes.db.test.ts`; `docs/trade-intent-transport.md` → GET /trading/intents/:id), и кроме `GET /trading/sessions/:id`, `POST /trading/sessions/:id/stop` (#283) и `POST /trading/sessions/stop` (#122): `readTradingSessionView` фильтрует по `telegram_user_id`, чужая сессия отвечает 404 как несуществующая; на том же 404 стоит inline-обработчик «📤 Поделиться» (#321, #538, `apps/bot/src/session-share.ts`): он читает `POST /trading/sessions/:id/share` с `inline_query.from.id`, и чужой или неизвестный id получает пустой inline-ответ (`session-share.test.ts` S2); стоп — чтение по владельцу, затем CAS по id; `waitingMessageId` тела снимает только ожидание с этим id той же строки (#587, `session-routes.db.test.ts` T11, T12, T12b); стоп всех — один UPDATE, где владелец — предикат (`stopUserSessions`), чужой id останавливает ноль сессий и отвечает `[]`, как «нет сессий» (`session-routes.db.test.ts` A5) (`session-routes.db.test.ts`, `trading-session-start.db.test.ts`; `docs/trading-session.md` → Routes); и кроме `POST /trading/sessions/:id/summary` (#318): владелец — условие самого CAS-UPDATE `claimSessionSummary`, чужая сессия отвечает тем же 409 `summary_unavailable`, что несуществующая, и ничего не пишет (`trading-session-start.db.test.ts` S9, `session-routes.db.test.ts` U3); и кроме `POST /trading/sessions/:id/share` (#538): владелец — в чтении view (`readTradingSessionView`) и в чтении сделок (`readSessionShareTrades`, `sessionOwnedBy`), чужая сессия отвечает 404 `not_found` до создания кода, как несуществующая; реферальный код создаётся только для `telegramUserId` тела (`session-routes.db.test.ts` H1–H3, `trading-session-start.db.test.ts` SH2); и кроме `POST /trading/sessions/:id/status-message` (#567): владелец — в предикате CAS `recordSessionStatusMessage` и в чтении view, чужая сессия ничего не пишет и отвечает 404 `not_found`, как несуществующая (`session-routes.db.test.ts` T4, `trading-session-ops.db.test.ts` M2); и кроме `POST /trading/sessions/:id/status-message/lost` (#567): владелец — в предикате CAS `forgetSessionStatusMessage`, чужой id отвечает `{ forgotten: false }`, как другое сообщение, и ничего не пишет (`session-routes.db.test.ts` T9, `trading-session-ops.db.test.ts` F3); `GET /trading/sessions/tracked` (#567) не скоупится — внутренний список восстановления трекинга бота: id сессий, telegram id владельцев, id сообщений, секретов нет (docs/trading-session.md → Routes); `POST /users/referral` (#115) скоупится по собственному `telegramUserId` вызывающего: отвечает код и число приглашённых только этого пользователя, неизвестный id — 404 `user_not_found` (`users/routes.db.test.ts` U3–U5). Сеть: запрос с заголовком прокси (`x-forwarded-for`/`-host`/`-proto`/`forwarded`) получает not-found 404 на любом маршруте, кроме помеченного `config.publicThroughProxy` (только `GET /postbacks/binodex/:secret`, #141) — корневой `onRequest` (`refuseProxied`) в `buildApp`, до bearer-хуков; enforced для каждого зарегистрированного маршрута — `postbacks/routes.db.test.ts` → the proxy guard (G1–G6); что внутренние вызывающие (bot, web, worker, healthcheck) не шлют этих заголовков и что прокси их ставит — stated (Caddy 2.6.2 — проба 2026-10-10, docs/postbacks.md → The proxy guard). Платежи Stars (#117, `payments/routes.ts`): плательщик сверяется с пользователем payload'а — в pre-checkout отказ `payer`, при зачислении `held` (`payer`): пересланный счёт оплачивает не его владелец (`payments/routes.db.test.ts`, `star-payment-ops.db.test.ts` S5). `/paysupport` (#118): список и заявка — по `star_payments.payer_telegram_user_id`, а не по строке `users`; чужой id платежа неотличим от отсутствующего (404 `payment_not_found`), фильтр — в самом `INSERT … SELECT` (`payments/routes.db.test.ts` P2, P5).
