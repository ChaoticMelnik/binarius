# Architecture Rules — trading

Торговля: переходы и исполнение `trade_intents`, сверка и сопоставление сделок, сессии и lease сокета брокера, торговые сессии, выключатель, размер ставки, DEMO_ONLY, режим торговли, строка `broker_trades`. Индекс — `.claude/skills/architect/SKILL.md` → Architecture Rules.

### Rule 6
6. **Переходы `trade_intents`** — только CAS внутри UPDATE (`status = from`, опционально `version` и предикат); возрастные предикаты — по часам БД (`trade-intent-ops.ts`). CAS — дисциплина операций (stated); единственный UPDATE `trade_intents`, не являющийся переходом, — `claimReconciling` (#89): статуса в SET нет (триггер не срабатывает), `version + 1`, предикат аренды, `reconcile_claimed_at = now()`; каждый UPDATE, меняющий `status`, идёт по ребру графа `TRADE_INTENT_TRANSITIONS` и поднимает `version` на 1 — enforced триггером `trade_intents_transition_guard` (`BEFORE UPDATE OF status`, миграция 0014; INSERT может нести любой статус — путь создания вставляет только `planned`, stated; копия графа сверяется сеткой всех пар в `schema.db.test.ts`, смена графа — новая миграция с `CREATE OR REPLACE FUNCTION`); «терминальный ⇔ резерв 0» — CHECK `trade_intents_terminal_reserve_check` (0013, из `TERMINAL_TRADE_INTENT_STATUSES`). Другие state machine'ы устроены иначе и этим правилом не покрыты: `outbox_events` — claim `for update skip locked` по `(id, status)`, затем update по `id` в той же транзакции (`apps/backend/src/outbox/store.ts`); `broker_accounts` — update по `id` под `FOR NO KEY UPDATE` в порядке блокировок, revocation по хешу refresh-токена там, где строка не заблокирована (`oauth-ops.ts`).

### Rule 15
15. **Executor:** `rejected` — только когда ордер точно не открылся; throw → `unknown`; `accepted` — только с `OpenTrade` брокера (`SubmitResult.accepted` требует `transport` и `trade`), совпадающей с intent'ом по режиму, активу, направлению и сумме, иначе `unknown` (`trade_mismatch`) — `markIntentAccepted` (`packages/db/src/trade-intent-ops.ts`) и `persistOutcome` (`apps/trading-worker/src/intents/processor.ts`), #17; `detail` только в лог, обрезается до `MAX_DETAIL_LENGTH` при логировании (`persistOutcome` в `apps/trading-worker/src/intents/processor.ts`; константа — `packages/broker-rest/src/rest.ts`, та же, что режет `detail` брокера в REST-клиенте; контракт — `executor.ts`). Реализация — `createTradeCommandExecutor` (#100, `apps/trading-worker/src/intents/trade-command-executor.ts`, docs/trade-executor.md): правило двух случаев — сокет, когда сессия аккаунта `ready`; REST только когда ничего не было отправлено (нет сессии или `not_sent`/`not_ready`); после emit — ответ сокета, `unknown`/`state_changed` или `unknown`/`timeout` по своему таймеру клиента `BROKER_SOCKET_COMMAND_TIMEOUT_MS` (5 с, #96), без повтора и без POST следом (`trade-command-executor.test.ts`, S3–S10); отправлено без ответа (emit или REST `unavailable`/`contract_violation`/`aborted`) — `unknown` с `broker_unavailable`, отказ (сокетный `fail`, REST 401/429/4xx, `ok: false` источника токена) — `rejected` с `broker_rejected`; ответ на команду — первый `open_trade.fail` её режима или первый `open_trade.success` её режима с asset/action/amount команды, на том же **непомеченном** соединении; несовпадающий `success` — не ответ; любая смена состояния клиента — `unknown`; команда без ответа на живом соединении (оборванная сигналом — дедлайн процессора тоже — или по таймеру команды) помечает соединение (`tainted`), клиент рвёт его сам (`engine.close()`), и до `ready` нового соединения `openTrade` отвечает `not_sent`/`not_ready` (#101; `BrokerSocketClient.openTrade`, `socket.test.ts` — поздний `fail` при удержанном через `openSocket` соединении не отвечает следующей команде, реальный разрыв даёт второе соединение, чужие условия `success` не ответ; `trade-command-executor.test.ts` S9). Ответ на другом сокете того же пользователя (рассылка брокером) не закрыт — `stated`, `BROKER_WS_URL` не задаётся до пробы двух сокетов (docs/broker-socket.md → Observed live).

### Rule 21
21. **Снимок баланса брокера (#137, #235).** `broker_balance_snapshots` — одна строка на аккаунт (FK `broker_balance_snapshots_account_fk`); пишут только операции `packages/db/src/balance-snapshot-ops.ts`, каждая — один autocommit-statement на `Db`. `*_observed_at`/`*_event_at` и возрасты — по часам БД; возраст будущей метки — 0, NULL остаётся NULL (`case … greatest(0, …)`); `fresh = min(restSnapshotAgeSec, balanceEventAgeSec ?? ∞) <= BROKER_BALANCE_SLA_SEC` (`isBalanceFresh`, `packages/shared/src/broker-balance.ts`). Запись проверяет домен колонок до statement'а и возвращает `{ written: false, field }` (`balanceSnapshotOutOfDomain`: суммы без знака, ≤ 12 целых и ≤ 8 дробных цифр; `level.rank` — по десятичной форме; `level.code` — 1–64 code points без управляющих символов, enforcement `partial`: только писатель, колонка без CHECK; `balance-snapshot-ops.db.test.ts`). Писатель сверяет `id` ответа брокера с `broker_accounts.broker_user_id` до записи (`balance-reconciler.db.test.ts`). Фоновый цикл: кандидаты — «аккаунты в работе» с валидным токеном, порядок `greatest(rest_observed_at, last_refresh_failed_at) asc nulls first` (`balance-snapshot-ops.db.test.ts`); попытка, не оставившая следа в строке (в том числе throw и `user_blocked`), откладывается в памяти на `BALANCE_STALLED_RETRY_MS`, неожиданная ошибка в тике логируется только через `errorLogFields` (`balance-reconciler.db.test.ts`). Писатели менеджера сессий (#101): `user.data` → `upsertBalanceSnapshot` (`eventAt` обоих режимов; `rest_observed_at` тоже сдвигается), `update_balance` → `applyBalanceEvent` (только существующая строка, три суммы режима и `<mode>_event_at`; нет строки → `no_snapshot`, вне домена → `out_of_domain` до statement'а; `balance-snapshot-ops.db.test.ts`); события без id пишутся только после `user.data` с `broker_user_id` аккаунта на том же соединении, чужой id снимает сессию в обработчике и ничего не пишется (`session-manager.test.ts` U9–U9c, `session-manager.db.test.ts`); REST-снимка при старте сессии и `refresh()` после `accepted` нет (`docs/broker-balance.md` → The socket writers). Проверка после исхода сверки (#92, `apps/trading-worker/src/intents/balance-check.ts`): токен с `mayRefresh: false`, один `GET /v1/broker/user`, сверка id до записи, запись через `upsertBalanceSnapshot` (домен — в операции; `eventsAfter` — часы БД первого чтения: режим с более новым сокетным событием сохраняет свои суммы), затем `held` против суммы наших открытых `broker_trades` режима в SQL `numeric` (`readHeldExposure`), режим сравнивается, только если между двумя чтениями вокруг GET ничего нашего не двигалось; алерт `broker balance mismatch` без сумм, без halt; триггеры — `accepted`/`settled`/`rejected`, не `manual_review` (`balance-check.db.test.ts` B1–B16, B5b, B6b; `trade-intent-ops.db.test.ts` H1–H6). Третий вызывающий `refresh` на backend'е — view завершённой сессии (#337, `viewForReply` в `apps/backend/src/trading/session-routes.ts`): `mayRefresh: false`, без `requested`, только при `isTradingSessionFinished`, `settled > 0` и снимке старше последней строки `settle` леджера сессии или без снимка (`current` в `readTradingSessionView`; оркестратор читает свой, более широкий фрагмент — `readSessionBalance` (#696): суммы режима сессии и `awaitsBalance` (settled intent аккаунта в режиме сессии — любой сессии или разовый — новее снимка и моложе лимита без сигнала, по `trade_intents.updated_at`) одним statement'ом; `current` view — только сделки своей сессии; `balance: null` — тоже refresh, G12); после `ok` предикат держится — не больше одного успешного GET на сессию, неудачный refresh повторяется каждым чтением view завершённой сессии (трекер, stop-роут, запасной текстовый итог сендера #537; stated) (`session-routes.db.test.ts` G5–G12, `trading-session-start.db.test.ts` V9).

### Rule 22
22. **Торговля за глобальным выключателем (#134 → #144).** Любой intent (demo и real) создаётся и уходит брокеру только при открытом `trading_switch` (одна строка, `packages/db/src/schema/trading-switch.ts`; предикат один — `tradingOpenSql`, `packages/db/src/trading-switch-ops.ts`): `createInTransaction` после replay и до чтения аккаунта и резерва (`trade-intent-ops.db.test.ts` P1–P4, `routes.db.test.ts` → 409 `trading_paused`); предикат `takeIntent` + `rejectPausedIntent` в процессоре после проверки срока (`processor.db.test.ts` W1–W5; ограда до `submitting`, Rule 15 не затронут; у `rejectPausedIntent` нет предиката выключателя — W5); `createTradingSession` после блокировки аккаунта (`trading-session-ops.db.test.ts` C7) и операция `stopPausedSessions` (S3) — первый sweep тика оркестратора (#287), до сигнала (`orchestrator.db.test.ts` K1); отказ `trading_paused` при создании intent'а сессии останавливает её как `kill_switch` (K2). Нет строки — закрыто (fail-closed, `trading-switch-ops.db.test.ts` T6). Новая БД — **открыто** (миграция 0020, `source = migration`, решение владельца 2026-10-07; T1). Открывает только `openTrading` (всегда `source = operator`): enforced — `trading_switch_open_source_check` (открытая строка только с `migration`/`operator`, `schema.db.test.ts`) + T8 (`trading-switch-writers.test.ts`). Автоматически закрывает circuit breaker worker'а (#96, `apps/trading-worker/src/circuit-breaker/`, docs/runbook-broker-outage.md): два сигнала — сабмиты без ответа брокера (`unknown`/`broker_unavailable` как результат транспорта — сокет `timeout`/`state_changed`, REST `unavailable`/`contract_violation` — через декоратор `observeExecutor`, executor не тронут; свои таймауты транспортов 5 с ниже пола дедлайна 6 с, поэтому молчание брокера считается всегда; сабмит, оборванный своим signal'ом (`aborted`), — нет) и потери сокетов (ready → не ready дольше `SOCKET_LOSS_GRACE_MS` (`session-config.ts`, монотонные часы менеджера), в том числе первое подключение после обновления токена, или `disconnected_by_server` после ready; не наши дропы и не `token_expired`/`auth_failed`; проверка `observeSessions` на своём таймере, каждая готовая сессия отмечается ready — знаменатель доли = все сессии, бывшие в работе за окно, снятые нами в том числе), окно по уникальным ключам с последним состоянием; сабмит, оборванный своим signal'ом (дедлайн, stop), не записывается, порог «≥ `CIRCUIT_BREAKER_MIN_FAILURES` и ≥ `CIRCUIT_BREAKER_FAILURE_PERCENT` %» за `CIRCUIT_BREAKER_WINDOW_MS` (env, звенья при импорте `circuit-breaker/config.ts` и в `env.ts`); срабатывание — single-flight `stopTrading(source = circuit_breaker)`, аудит `via: circuit_breaker` (T2b), окно очищается; никогда не открывает (CHECK); окна — на процесс (несколько worker'ов — #94). Тесты — `circuit-breaker/*.test.ts` W1–W6, B1–B6, D1–D5; `session-manager.test.ts` S1–S9; `trade-command-executor.test.ts` S10. Replay first. Окно между коммитом `kill-switch on` и уже начатыми statement'ами (создание, `takeIntent`) — stated. Env-флага real-режима нет (#134 удалён): real от demo отделяет режим пользователя — Rule 36, и проверки брокера на его стороне (не проверено); на стенде — ещё `DEMO_ONLY`, Rule 33. Пер-аккаунтные проверки создания (пользователь `active`, аккаунт `active` и не `trading_halted`, токены, один живой intent) действуют одинаково для обоих режимов. Переключатель — CLI `kill-switch` (`docs/kill-switch.md`), каждое изменение — строка `audit_log` в той же транзакции.

### Rule 23
23. **Размер ставки v1 (`packages/stake/src/`, `@binarius/stake` с #775; читают оркестратор и H1-драйвер backend'а, `sessionTradeOf` — единственное отображение intent'ов сессии в сделки сайзера, `sessionStakeInput` — единственный вход сайзера обоих создателей: история, payout, минимум, available, `nowMs`, прижатый к `started_at`; `history.test.ts` ST4–ST5).** Решение — чистая функция от параметров и входа (`createStakeSizer`, `size.ts`): без часов, сети, БД и логов. Деньги — `DecimalString` на входе и выходе, арифметика — `bigint` со шкалой 8 (`money.ts`, домен 12/8 сверен с `tradeAmountSchema` в `money.test.ts`); payout брокера (`number`) становится целым шкалы 4 через `String()` без арифметики (`parsePayout`); JS-float для денег не создаётся, `bigint` в решение не попадает (`size.test.ts`, JSON round-trip). Превышение лимита, ставка ниже `min_trade_amount` или выше `available`, неразрешённая заявка в истории и непригодные данные — `stop` с кодом из `StopReason` (`codes.ts`) в фиксированном порядке проверок, никогда подгонка ставки и никогда пропуск шага; throw — только на неверные параметры (`assertStakeParams`, при импорте для `DEFAULT_STAKE_PARAMS`) и неверные часы. Шаг Мартингейла — наименьшая ставка на шкале `stakeScale`, чей профит `floor_s(stake × payout/100)` покрывает `ceil_s(убыток серии + профит базовой ставки)` (`size.test.ts`, сетка через `next()`); кандидат выше `maxStake` останавливается до форматирования, поэтому `amount` ставки всегда проходит `tradeAmountSchema` (`size.test.ts`, S20 и S21). Лимиты Мартингейла обязательны по типу `StakeParams` и в `assertStakeParams`; `DEFAULT_STAKE_PARAMS` (сайзер без параметров, только тесты сайзера) — `fixed`. Мартингейл — стратегия сессий по умолчанию (#450): `SESSION_STAKE_STRATEGY` (`parseSessionStakeStrategyEnv`, `martingale` | `fixed`, нет — `martingale`, иное и пустое — ошибка старта; `env.test.ts`) читают только старт-роут (deps `stakeStrategy`) и CLI `session-start`; оба пишут settings v3 (#552; до него v2) одним `buildSessionSettings`, для `martingale` — с `martingaleLimitsFor(baseStake)` (`packages/shared/src/trading-session.ts`, единственное место множителей: `maxSteps` 4, `maxStake` 12×B, `maxSessionLoss` 20×B, `maxSessionDurationMs` = `SESSION_MAX_DURATION_MS`; умножение — `multiplyDecimal`, `bigint` шкалы 8; пин — `trading-session.test.ts`; 12× вместо «~10×» владельца — решение менеджера 2026-10-15, docs/stake.md → Defaults); `MARTINGALE_MAX_STEPS` — и множитель шагов худшего случая `sessionFitsDeadline` (#552): сессия заканчивается на N-м закрытом цикле, не на N-й сделке, лимиты сайзера остаются технической причиной остановки (Rule 28). Стратегия и лимиты замораживаются в строке при старте: оркестратор env не читает (параметра нет — tsc) и строит сайзер только из `sessionStakeParams(settings)`, v1 — `fixed` (`orchestrator.db.test.ts` G1–G8, `session-routes.db.test.ts` R40–R41, `start.test.ts` C8, `session-start.db.test.ts`). Подключение — оркестратор #287 (`trading-session/orchestrator.ts`): история → `SessionTrade`, баланс режима сессии; четыре лимит-стопа (`max_steps_exceeded`, `max_stake_exceeded`, `max_session_loss_exceeded`, `session_duration_exceeded`) — свои `stop_reason` через `STAKE_STOP_REASONS` (`satisfies Record<StopReason, TradingSessionStopReason>`, G3–G6), остальные коды — `stake_stop` с кодом в строке лога (E3, G8; `insufficient_balance` при `awaitsBalance` — hold `TRADING_SESSION_TICK_MS`, #696); `nowMs` прижат к `started_at` (E11). Сообщения сделок (#464) берут стратегию тем же `sessionStakeParams` (`session-notice-messages.test.ts`). Env у сайзера нет.

### Rule 24
24. **Проход сверки (#89, `apps/trading-worker/src/intents/reconciliation.ts`).** Кандидаты — `status = reconciling and (reconcile_claimed_at is null or reconcile_claimed_at < now() − RECONCILE_RETRY_MS)`, порядок `reconcile_claimed_at asc nulls first` (один SQL-фрагмент `reconcileLeaseExpired` для списка и claim'а, `trade-intent-ops.ts`). Claim (`claimReconciling`) — первая запись каждой попытки, до обращения к брокеру: ни один исход не оставляет ключ порядка на месте (`reconciliation.db.test.ts`). `accepted` из `reconciling` — только через `concludeReconciled` с найденной сделкой брокера (закрытая — `accepted → settled` в той же транзакции); единственное освобождение резерва из `reconciling` — `rejectIntent` на `not_found` реконсилера (`reconciliation_not_found`); `not_found` отвечает только `createRestReconciler` и только для demo (#274): окно закрыто по `reconcile_claimed_at`, ноль точных и near-кандидатов, `last_error ≠ trade_mismatch`, первая страница (`offset=0`) каждого списка — пустая или из сделок с разными id, первая строго новее последней, одна старше окна, все сделки режима intent'а, — и так две не прерванные попытки подряд разных claim'ов, чтения которых разнесены не меньше чем на `RECONCILE_RETRY_MS − RECONCILE_ATTEMPT_TIMEOUT_MS` (счётчик в памяти реконсилера; любой другой исход и throw не прерванной попытки его сбрасывают, прерванная попытка его не трогает; рестарт обнуляет); первая такая попытка — `unavailable`/`absence_unconfirmed`; real и отсутствие доказательства — `unresolved` → `manual_review` (`reconciliation_not_found`) + halt (`rest-reconciler.test.ts` P/C/R-NF2, `reconciliation.db.test.ts` E1–E3, `orchestrator.db.test.ts` R2, R2r; посылки A1/A3/A4/A5/A7 (первая страница — новейший префикс списка) — `docs/broker-rest.md` → Observed live (2026-10-23); stated, кодом не проверяются); `unavailable`, дедлайн попытки и throw не пишут ничего, кроме claim'а; каждый исход — CAS по `status = reconciling` и `version` из claim'а (`trade-intent-ops.db.test.ts`, `reconciliation.db.test.ts`). ### Rule 25

### Rule 32
32. **Lease сокета брокера (#93, `packages/db/src/session-lease-ops.ts`, `apps/trading-worker/src/broker/session-manager.ts`, docs/broker-session.md → The lease).** Одна строка на аккаунт в `broker_session_leases` (PK `broker_account_id`, CHECK `broker_session_leases_expiry_check`, FK restrict; `schema.db.test.ts`); каждая операция — один autocommit-statement на `Db` вне цепочки блокировок Rule 5, часы БД. Захват — `insert … on conflict do update … where expires_at <= now() or owner_id = excluded.owner_id`: свободный, истёкший или свой; два одновременных захвата одного ключа — ровно один победитель (`session-lease-ops.db.test.ts` A1–A5, граница `<=` — A4 внутри одной транзакции); продление — только свои и только живые (истёкший = потерянный), ни продление, ни свой перезахват не укорачивают lease (`greatest`: statement, закоммиченный последним, не отменяет более позднего, R1–R5); освобождение — только свои, только при `stop()` после закрытия всех клиентов (D1, L8). Менеджер: захват до запроса токена, с таймаутом продления (L1–L3, L14), продление одним statement'ом раз в `SESSION_LEASE_RENEW_MS` только записей с отвеченным захватом (L10), с таймаутом `SESSION_LEASE_RENEW_TIMEOUT_MS < RENEW` (L13), ответ — к аккаунту, у которого тот же объект lease, общий для записей starting и running (L9, L11, L12), пропавший id — немедленный drop (L4); fence по монотонным часам: `sessionFor` не отдаёт клиент после `t0 + SESSION_LEASE_FENCE_MS` даже до срабатывания таймера (L5), таймер закрывает сокет (L6), одно неудачное продление не закрывает (L7); после ответа токена клиент не стартует за fence — ни в `startOne`, ни в `refresh()` (L15, L16); гарантия «одно неудачное продление не закрывает»: `2 × RENEW + 2 × RENEW_TIMEOUT < FENCE < TTL < SESSION_RETRY_MS`, `RENEW_TIMEOUT < RENEW` — в `sessionManagerConfigHolds` при импорте (`session-config.test.ts`). Критерий «два процесса не держат сокет одного аккаунта» — `session-lease.db.test.ts` M1 (только захват, фильтр кандидатов выключен), перехват после смерти владельца — M2. Фильтр кандидатов по `ownerId` — оптимизация, не гарантия. Fencing на стороне брокера нет: процесс, замёрзший дольше FENCE, держит TCP до пробуждения — stated (docs → Accepted risks 5). Две реплики — в окне деплоя с перекрытием (#95, docs/worker-deploy.md → The overlap's length): от старта нового контейнера до выхода старого — ожидание готовности (до `READY_TIMEOUT_S`, 120 с) плюс drain старого (≤ 40 с), а после прерванного или упавшего прогона — до вмешательства оператора (скрипт отказывает, пока у сервиса есть второй контейнер в любом состоянии); `stop()` старого процесса удаляет его строки после закрытия всех клиентов, скан нового пропускает живые чужие lease и берёт аккаунт на следующем тике (`worker.handoff.db.test.ts` H2: не больше одного сокета на пользователя брокера при каждом опросе); `dirty`-выход ничего не освобождает, lease истекает по TTL. ### Rule 36
36. **Режим торговли пользователя (#121, docs/trading-mode.md).** `users.trading_mode` — `text not null default 'demo'` + `users_trading_mode_check` из `TradeMode` (Rule 1; `schema.db.test.ts`). Единственный писатель — внутренний `writeTradingMode` (`packages/db/src/user-ops.ts`): UPDATE с `trading_mode <> $mode` и строка `audit_log` `trading_mode_changed` в той же транзакции; его вызывают два места: `setTradingMode` (пользователь: `actor_type = user`, `{ from, to }`; повтор того же режима ничего не пишет; блокирует строку `users`, затем active-сессии пользователя, затем закрывает ожидающие депозиты пользователя `superseded` при `changed: true` — `user-ops.db.test.ts` U-mode 1–8, U-dep 9, 10) и `switchTradingModeOnDeposit` (#686, docs/trading-mode.md → The automatic switch after a deposit: `actor_type = system`, `actor_id` NULL, `{ from, to, depositEventId }`; только demo → real); «только через `writeTradingMode`» — stated. Переход после депозита: проход backend'а `createDepositModeSwitcher` (`apps/backend/src/trading/deposit-mode-switch.ts`, тик `DEPOSIT_MODE_SWITCH_SCAN_MS`) над строками `deposit_events` с `user_id` и без исхода; `DEMO_ONLY` → `demo_only` до блокировки `users` (Rule 33, U-dep 8); под `users FOR NO KEY UPDATE`: `blocked` → `user_blocked`, `real` → `already_real` (без аудита и сообщения), аккаунт депозита не `active` → `account_inactive`, сессия не `stopped` на любом аккаунте пользователя → ничего (ждёт конца сессии, сессия доигрывает), иначе `writeTradingMode` + `switched` в одной транзакции; исход — один на строку (CAS `mode_switch is null`, U-dep 12; один платёж — одна строка, Rule 7); после коммита — `wakePlan()` движка рассылок (Rule 19); throw кандидата — `warn` и hold-back `DEPOSIT_MODE_SWITCH_RETRY_MS` в памяти (`deposit-mode-switch.test.ts` W1–W8, `deposit-mode-switch.db.test.ts` X1–X5, `user-ops.db.test.ts` U-dep 1–12, L1–L3). Real-intent создаётся только для пользователя в режиме `real`: предикат в резервирующем UPDATE `createInTransaction` (та же строка, что берёт блокировку — окна со сменой режима нет), диагноз по свежему чтению: `user_blocked`, затем 409 `real_mode_off`, затем `insufficient_tokens`; replay — до проверки (`trade-intent-ops.db.test.ts` M1–M4, `routes.db.test.ts`). Ограда односторонняя: demo-intent режимом не отклоняется — «один режим за раз» для кнопок бота держат чтение access и отпечаток кнопки с режимом (`demo.test.ts`, `demo-trade.test.ts`). Сессии — только в режиме пользователя (#327): `checkTradingSessionStart` и `createTradingSession` под блокировкой `users` (`mode_not_allowed`); смена режима останавливает active-сессии пользователя в транзакции `setTradingMode` (`stopUserSessions`, `user_stopped`; `user-ops.db.test.ts` U-mode 6–8, `trading-mode.db.test.ts` T9); `POST /trading/mode` отвечает `stoppedSessions` (T9, T10). Гейт резерва односторонний: real-intent сессии после перехода в demo отказывает `real_mode_off` до блокировки сессии, и оркестратор заканчивает попытку `account_unavailable` (`orchestrator.db.test.ts` E9i, E9j); demo-сессию после перехода в real заканчивает сам `setTradingMode`. `POST /trading/mode`: demo — всегда (кроме 404), real — `demo_only`, затем единственный активный аккаунт со снимком и `real.available >= minTradeAmount` (`decimalLessThan`, bigint); чтение и запись не атомарны — stated, на реальный ордер сверх баланса отвечает брокер (`trading-mode.db.test.ts` T1–T10). Сумма real-сделки бота — `realStake ?? minTradeAmount` (`effectiveStake`, #326), пикер — по режиму своих данных (Rule 29). Экран режима в боте (#474, `apps/bot/src/trading-mode.ts`, `trading-mode.test.ts`) — единственный путь бота к `POST /trading/mode` (`BackendClient.setTradingMode`; тело без `stoppedSessions` — `ContractViolation`, `backend-client.test.ts`): кнопка «⚙️ Режим торговли» `/settings` и сообщения о переходе после депозита (`mode`, `MODE_CALLBACK_DATA` в `packages/shared/src/bot-navigation.ts`; на карточке кнопки режима нет с #686) открывает экран и сама не переключает; подтверждение real (`mode:r`) — по новому чтению access, сумма `realStake ?? minTradeAmount`, при `real.available < minTradeAmount` (`decimalLessThan`) — сразу `modeBelowMinimum` без кнопки подтверждения, сумма вне `checkStake` — строка-предупреждение, включение не запрещено (MC1–MC7); отмена (`mode:x`) перерисовывает подтверждение в экран на месте, «✅ Подтверждаю» исчезает (MX1); неотменённое подтверждение живёт без срока — принятый риск (решение 23 #121, stated); возврат в demo — одним нажатием без подтверждения; текст итога — по режиму из ответа сервера, строка об остановке сессии — при `stoppedSessions >= 1`; отказы — `SWITCH_REFUSALS` (`satisfies Record<TradingModeErrorCode, …>`, tsc); неизвестный исход (5xx, обрыв, тело вне схемы) — повторное чтение access, не вывод из отказа; записи `mode:r:ok`/`mode:d` — в `WRITE_CALLBACK_PREFIXES`, под каждым отказом «⚙️ Режим» и меню, ни одной кнопки переключения (MW1–MW8, MR1). Тексты real-пути бота не называют сделку демо: общие экраны (сигналы, ручной выбор, сводка пары) — нейтральные дефолты, анализ — по режиму (`analysisDisclaimerReal`; строки порога цикла нет с #631), «➕ Ещё» несёт режим текста (`:d`/`:r`) и рисует кнопку ставки только при совпадении с режимом чтения при раскрытии (`demo.test.ts`); сцены real-пути проверяет `real-path.test.ts` на дефолтах каталога (с #326 — и реальный пикер; `/settings` называет оба режима по решению владельца и сценой не является) — переопределения сотрудников не проверяются (stated), новый экран real-пути добавляется в список сцен (stated). ### Rule 50
50. **Домен строки `broker_trades` (#675, `packages/db/src/schema/columns.ts`, `trade-intent-ops.ts` → `tradeRow`/`markIntentAccepted`, docs/trade-intent-transport.md → The row's domain).** Значение брокера, которое колонка не вмещает, не отклоняет запись принятой сделки: `payout` (`numeric(8,4)`, с 0077 nullable) пишется через `payoutInColumn` — NULL вне `[0, PAYOUT_MAX]` (9999.9999; тот же гард, что у `signal_decisions.payout`, Rule 42); `potential_profit` — через `moneyInColumn` — NULL вне формы `MONEY_SHAPE` (без знака, ≤ 12 целых и ≤ 8 дробных цифр; CHECK `>= 0`: сделка с выплатой 0 даёт 0); `raw` хранит значение брокера. CHECK'и цен `open_price`/`close_price` — только «конечное» (`finiteFloat`/`nullableFiniteFloat` отвергают NaN и ±Infinity), знак и 0 допустимы: на цене не стоит ни одно решение — её печатают (`session-texts.ts` → `priceOf`, экспорт) и масштабируют в график (`apps/bot/src/session-card.ts`, `session-promo.ts`; любое конечное значение). Домен не расширяется там, где значение входит в поведение: `open_timestamp_ms`/`close_timestamp_ms` — `> 0` (провод `unixMsSchema` пропускает 0 — stated), `profit` — `numeric(20,8)` и не NULL на закрытой строке (`broker_trades_settlement_check`, суммы сайзера и уведомлений; переполнение от 10^12 — stated, граница: ставка ≥ 10^10), `asset_id`/`amount`/`action`/`mode` — равенство с intent'ом (`mismatchOf`). Провод (`openTradeWireSchema`, `closedTradeWireSchema`) не сужается: отказ там уронил бы весь список сделок аккаунта (`tradesListWireSchema`) и остановил сверку. Enforced: `columns.test.ts` C1–C4, `trade-intent-ops.db.test.ts` D1–D12, `schema.db.test.ts` (строки домена `broker_trades`), `trade-log.db.test.ts` X16; текстовые колонки и NUL — stated.
