# Architecture Rules — core

Общие инварианты: статусы, деньги и токены, append-only, владение строк, порядок блокировок, идемпотентность, логирование ошибок, ответы HTTP, таймауты, env, миграции, валидация на границах, отметки времени. Индекс — `.claude/skills/architect/SKILL.md` → Architecture Rules.

### Rule 1
1. **Статусы.** Статусная колонка — `text` + CHECK из одной `as const`-константы на домен (`inList` в `packages/db/src/schema/columns.ts`); SQL-сравнения со значением — только через `literal()`/`sqlLiteralList`. Enforcement `partial` — ESLint `local/no-status-literal` (`tooling/eslint-rules/no-status-literal.ts`) вне файла определения константы ловит литерал (и template-литерал без подстановок) в позиции, чей тип — ровно множество значений константы: присваивание, аргумент, return, значение поля, `===`/`!==`/`==`/`!=` и `case` по объявленному типу (`s`, `row.prop`, `row['prop']`), а также `'значение'` из `[a-z0-9_-]` внутри `sql`-шаблона или `sql.raw`. Не ловит: вычисляемый доступ `row[key]` (сравнение идёт с суженным типом), позицию, типизированную шире (`string`) или подмножеством значений, нетипизированные копии списка (например, `z.enum([...])` без ссылки на константу), литералы в `*.test.ts`.

### Rule 2
2. **Деньги и токены.** Токены — `bigint` (`tokenAmount`, `columns.ts`), денежные суммы — `numeric(20,8)` в string-mode из одного `money()` (`columns.ts`, все денежные колонки, #137) с CHECK против `NaN` (`positiveNumeric`; для сумм, которые бывают нулём, — `nonNegativeNumeric`; для nullable — `nullablePositiveNumeric`, как `users.demo_stake` и `users.real_stake`, #297, #326), в коде — `DecimalString` из `@binarius/shared`; JS `number`/float для них не используется. На границе брокерского wire JSON-число становится `DecimalString` только в `moneyWireSchema` (`packages/shared/src/money.ts`), через `String()`, без арифметики: целое — только safe-int; дробное (#236) — только если `String()` даёт простую десятичную запись не длиннее `MAX_WIRE_SIGNIFICANT_DIGITS` (15) значащих цифр; `NaN`, `±Infinity`, целые от 2^53, экспоненциальная запись и 16+ значащих цифр отвергаются; текст с > 15 значащими цифрами, который `JSON.parse` округлил до короткого double, неотличим и принимается (`money.test.ts`). Ту же схему использует `partnerTraderStatsWireSchema.balance` (Partner API live не проверялся, #14). Единственное место, где JS `number` для денег создаётся намеренно, — `wireMoney` в `packages/mock-broker/src/money.ts`: фикстура изображает провод брокера и строит число из десятичного текста центов, без арифметики (`money.test.ts` мока). Кэш `users.token_balance`/`token_reserved` равен суммам `token_ledger` и пишется в одной транзакции со строкой леджера — `createInTransaction`, `releaseTokens`, `applyBonus` (#13, `bonus-rule-ops.ts`: бонус по действующей версии правила, Rule 40; стартовый пакет — через `grantLinkBonus`, награда пригласившему — через `grantReferralReward` (#116, `referral-reward-ops.ts`, строка и `token_balance` пригласившего под его `users FOR NO KEY UPDATE`; равенство — `referral-reward-ops.db.test.ts`), депозитный бонус #386 — через него же; id версии и сумма — из одного чтения строки), `consumeTokens` (`settleIntent`, #17: `settle` = `reserved_delta −1`, `balance_delta −1`), `adjustTokens` (#246, `token-adjustment-ops.ts`: `users FOR NO KEY UPDATE`, отказ ниже резерва до statement'а, предикат UPDATE — backstop), `creditStarPayment` (#117, `star-payment-ops.ts`: покупка за Telegram Stars, `users FOR NO KEY UPDATE`, строка `purchase` и `token_balance += tokens` только при вставке своей строки `star_payments`), `recordStarRefund` (#118, `star-payment-ops.ts`: возврат Stars, `users` → `star_payments` `FOR NO KEY UPDATE`, строка `refund` и `token_balance −= taken`, taken = `min(tokens, token_balance − token_reserved)`, предикат UPDATE — backstop, CAS статуса `paid | held` → `refunded`; своей строки аудита не пишет — `stars_refunded` пишет вызывающий в той же транзакции, payload из одного `starsRefundedPayload`: `recordStarRefundBySystem` (CLI и сверка, актор `system`, `star-payment-ops.db.test.ts` R1, R3, R4) и `recordStarRefundByStaff` (админка #510, актор `'admin'` и id сотрудника, `admin/routes.db.test.ts` SR2; без строки от писателя — R10)); читается одним statement через `readTokenBalance` (`packages/db/src/token-balance-ops.ts`, #136). Равенство для этих семи writer'ов проверяют `token-balance-ops.db.test.ts` (#117: покупка и её повторная доставка; #118: возврат и его повторная запись) и `token-adjustment-ops.db.test.ts`; для будущих writer'ов правило stated, не enforced — триггера нет. `note` обязателен и ограничен для `adjustment` — CHECK `token_ledger_adjustment_note_check` (1..`TOKEN_LEDGER_NOTE_MAX` code points, enforced, `schema.db.test.ts`); лимит `|delta| ≤ TOKEN_ADJUSTMENT_MAX_TOKENS` — `checkTokenAdjustment` в zod роута и в писателе, не CHECK (stated).

### Rule 3
3. **Append-only.** `token_ledger` и `audit_log` отвергают UPDATE, DELETE и TRUNCATE — row- и statement-триггеры (`packages/db/drizzle/0001_append_only.sql`). `bonus_rules` (#13) — неизменяемые строки, не append-only: `bonus_rules_immutable` отвергает UPDATE любого столбца, кроме `is_active`, `valid_from`, `valid_to`, `updated_at`; `bonus_rules_no_delete` и `bonus_rules_no_truncate` — DELETE и TRUNCATE (`0059_bonus_rules.sql`). Enforced: гейт покрытия в `schema.db.test.ts` требует наблюдать все семь триггеров. **Единственный санкционированный обход `token_ledger_append_only`** — бэкфилл миграции 0059 (#13): за guard'ом на `bonus` без `broker_account_id` — `DISABLE TRIGGER`, один UPDATE `bonus_rule_id`/`bonus_rule_kind` стартовых пакетов на `link_bonus` v1, `ENABLE TRIGGER`, всё в транзакции мигратора (`migrate` drizzle-orm выполняет все ожидающие миграции в одной); оба триггера леджера включены после, UPDATE снова отвергается — `bonus-rules-migration.db.test.ts`. Другая миграция триггер не отключает. Рост `audit_log` ограничен писателями, не ретенцией (#153): анонимные пути входа строк не пишут (логин, которого ни у кого нет, и challenge id, никому не выданный, — только `info` лога с `reason`, без имени и id), отказ по известной сущности с публичной формы — одна строка на событие через `writeAuditEntryOnce` (`staff-ops.ts`; блокировка — по `lockedUntil`, challenge — по (id, reason), ссылка #448 — по (id, reason)) под блокировкой строки сущности. Enforced: `staff-ops.db.test.ts` (`recordLoginLockout: one row per lockout`, `one row per (challenge, reason)`, «refuses a challenge id nobody issued and leaves no row»), `staff-link-ops.db.test.ts` (`refuseLink: one row per (link, reason)`), `routes.db.test.ts` (строки лога, ни строки таблицы для анонимных путей); для будущих анонимных писателей — stated.

### Rule 4
4. **Владение строк — композитными FK**, не проверками в коде: `trade_intents_account_owner_fk`, `trade_intents_session_account_fk`, `deposit_events_account_owner_fk`, `deposit_events_account_trader_fk` (#141: депозит называет только аккаунт своего `broker_user_id`; цель — `broker_accounts_id_broker_user_id_key`), `token_ledger_intent_owner_fk`, `token_ledger_deposit_owner_fk`, `token_ledger_star_payment_owner_fk` (#117: строка леджера называет платёж Stars своего пользователя; цель — `star_payments_id_user_key`; та же для строки `refund`, #118), `token_ledger_bonus_rule_fk` (#13: `(bonus_rule_id, bonus_rule_kind) → bonus_rules (id, kind)`, цель — `bonus_rules_id_kind_key`; вид, которого требует ссылка строки, закрепляет `token_ledger_bonus_rule_check`, а FK — что названная версия этого вида; `schema.db.test.ts`), `token_ledger_referral_inviter_fk` (#116: `(referral_id, user_id) → referrals (id, inviter_user_id)`, цель — `referrals_id_inviter_key`; награда — только на леджере пригласившего этого приглашения; `schema.db.test.ts`), `broker_trades_intent_account_fk`. Не композитный, по смыслу: `star_refund_requests_payment_fk` (#118, `restrict`) — заявка принадлежит плательщику, а не строке `users`; плательщика проверяет `INSERT … SELECT` по `payer_telegram_user_id` (Rule 13).

### Rule 7
7. **Идемпотентность:** unique `(user_id, client_request_id)` (`trade_intents_user_request_idx`, миграция 0002); не больше одного нетерминального intent'а на аккаунт (`trade_intents_active_account_idx`); outbox — unique `(topic, intent_id)` (`outbox_events_topic_intent_key`); сделка брокера привязывается к intent'у ровно один раз — `broker_trades_account_trade_key` + `broker_trades_intent_id_key` (#17), терминальных строк леджера (`release`/`settle`) — не больше одной на intent (`token_ledger_terminal_intent_idx`); что она есть — правило писателей (`rejectIntent`/`settleIntent` читают резерв под блокировкой и пишут строку при > 0), stated. Постбэки (#141): одна доставка на `(source, postback_id)` — `postback_deliveries_source_postback_idx`, частичный `where outcome <> 'rejected'` (отклонённая доставка слот не занимает); один депозит на `(source, payment_id)` — `deposit_events_source_payment_idx`; один бонус на депозит — `token_ledger_deposit_event_idx` (`postback-ops.db.test.ts` P1–P3). `adjustment` — без ключа дедупликации в БД; повтор формы ловит `expectedBalance` писателя (В4 #246, stated; `routes.db.test.ts` — повторная отправка той же формы получает `balance_changed`). Покупка за Stars (#117): ключ — charge id Telegram, `star_payments_charge_key` (вставка первой: зачисляет только вставивший), второй барьер — `token_ledger_star_payment_idx` `(star_payment_id, kind)`, второй слот — возврат #118 (`star-payment-ops.db.test.ts` S1, S2; `schema.db.test.ts`). Возврат (#118): барьер — статус под блокировкой строки платежа и CAS `paid | held` → `refunded`; второй барьер на стороне леджера — тот же `token_ledger_star_payment_idx`; возврат без снятых токенов строки леджера не пишет, и его держит только CAS (`star-payment-ops.db.test.ts` R4, R6). Заявка `/paysupport` — одна на платёж, `star_refund_requests_payment_key`, `on conflict do nothing`. Бонусы (#13): бонус дедуплицируется своей ссылкой — стартовый пакет `token_ledger_link_bonus_user_idx`, депозитный `token_ledger_deposit_event_idx`; награда пригласившему (#116) — `token_ledger_referral_idx` (частичный unique `(referral_id)`, arbiter `ON CONFLICT`), то есть одна на приглашение, а с `referrals_invitee_key` и `broker_accounts_broker_user_id_idx` — одна на приглашённого и на `broker_user_id` (`referral-reward-ops.db.test.ts` W3, W4, L3; `schema.db.test.ts`); бонус без ссылки (промо) отвергает `token_ledger_bonus_rule_check` (`else false`); смена версии правила ключи не расширяет, поэтому уже начисленное повторно не начисляется (`bonus-rule-ops.db.test.ts` → a rule change).

### Rule 8
8. **Ошибки логируются именем и кодом** через `errorIdentity`/`errorLogFields` (`packages/shared/src/logging.ts`). Enforcement `partial` — ESLint `no-restricted-syntax` (`eslint.config.js`; комментарий там — источник этого списка) видит поле `err`/`error`/`cause`/`exception` в первом объекте вызова логгера, в том числе у логгера, взятого в переменную (`const l = request.log; l.error({ err })`), и positional error по имени переменной. Не видит: вложенный объект (`{ ctx: { err } }`), объект вторым аргументом, computed key, `logger[level](error)`, метод логгера в переменной, spread, positional error в переменной, не названной как ошибка, `new Error(x)` позиционно. Redact-пути покрывают глубину 0–5 (`LOG_REDACT_PATHS`); строку они не чистят. Runtime-сеть (#85): все четыре процесса собирают pino-логгер через `logOptions` (backend и web отдают его Fastify как `loggerInstance`); сериализаторы ключей `LOG_ERROR_KEYS` (`err`, `error`, `cause`, `exception` — тот же список строит regex ESLint-правила) сводят значение на верхнем уровне лог-объекта к `{ name, code?, cause?: { name, code? } }` (cause — вложенно, в отличие от соседнего ключа у `errorLogFields`); объект проходит своим `name`, только если уже имеет форму identity (литерал с собственными ключами лишь `name`/`code`/`cause` той же формы), иначе — `typeof`; `hooks.logMethod` подставляет фиксированное `msg`, где pino скопировал бы `err.message`. Сеть не покрывает: ошибку под другим или вложенным ключом, format-аргумент (`%s`/`%o`), свободный текст сообщения, явно переданное сообщение (`error.message` в `defaultErrorLog`/`writeHeadError` Fastify — поэтому `SafeLogController` в backend остаётся, в web эти строки отключены `disableRequestLogging`). Логгеры, которые тесты строят сами (`pino()` без `logOptions`), — вне сети. Отказ Bot API — одна функция `telegramErrorFields` (`packages/shared/src/telegram-logging.ts`, #155) для бота и backend'а: по форме, без grammY (`Error` со строковыми `method` и `description` и числовым `error_code` — по полям, не по имени, как `instanceof` — → `{ method, telegramErrorCode }`; `name === 'HttpError'` с полем `error` → переданный `method` и `transportError: errorIdentity(error.error)`; иначе — только переданный `method`), `description` и `payload` не возвращаются никогда; enforced — `telegram-logging.test.ts` (форма), паритет с настоящими классами grammY — тесты по строкам лога (`apps/bot/src/logging.test.ts`, `apps/backend/src/admin/telegram.db.test.ts`). Вызовы Bot API, которые grammY ретраит сам и молча (`getUpdates` в цикле поллинга — всё, кроме 401/409; `getMe` и `deleteWebhook` при старте), у обоих поллеров — `apps/bot/src/bot.ts` и `apps/backend/src/admin/telegram.ts` — проходят через `createTelegramRetryLog` (`packages/shared/src/telegram-retry-log.ts`, #67): каждый сбой — `warn` с `errorLogFields` и `telegramErrorFields`, `failures`, `elapsedMs`, после 429 — `retryAfterS`; первый успех после серии — `info` с `downMs`; long poll, оборванный собственным `stop()`, не логируется. ### Rule 26
26. **Тело HTTP-ответа — с потолком байтов (#234).** Серверные fetch-клиенты проекта — REST брокера (`packages/broker-rest/src/rest.ts`), OAuth брокера (`apps/backend/src/broker/oauth-client.ts`), backend-клиенты бота и web (`apps/bot/src/backend-client.ts`, `apps/web/src/backend-client.ts`), токен и источник пар worker'а (`apps/trading-worker/src/broker/access-token.ts`, `apps/trading-worker/src/trading-session/backend.ts`) — читают тело только через `readBody(response, maxBytes)` (`packages/shared/src/http-body.ts`): байты считаются по мере прихода, сверх потолка чтение отменяется и возвращает `undefined`, `content-length` не учитывается. Потолки: REST — `MAX_SUCCESS_BODY_BYTES` 4 MiB / `MAX_ERROR_BODY_BYTES` 16 KiB (`rest.test.ts` → body size); OAuth — `MAX_OAUTH_BODY_BYTES` 64 KiB для 2xx, тело ошибки не читается (`oauth-client.test.ts` → body size); бот, web, worker — по своей `MAX_BACKEND_BODY_BYTES` 1 MiB для 2xx и ошибки, `GET /bot-texts` в боте и пять методов «Тексты бота» в web — `MAX_BOT_TEXTS_BODY_BYTES` 16 MiB, `GET /trading/sessions/tracked` в боте (#567) — `MAX_TRACKED_SESSIONS_BODY_BYTES` 2 MiB (2 000 строк в самом длинном виде — около 360 KB, больше четверти 1 MiB) (`backend-client.test.ts` ×2, `access-token.test.ts` и `trading-session/backend.test.ts` → body size). 2xx сверх потолка — `contract_violation`; тело ошибки сверх потолка — у бота и web решает статус (`reason` нет), у токена worker'а 404/409 — `contract_violation`, прочие — `backend_status`, у источников сигнала и пар 503 пар — `contract_violation`, прочие — `backend_status`. Enforcement `partial`: тесты «сверх потолка», «бесконечное тело» и «самый длинный ответ под объявленными допущениями» у каждого клиента; таблица последнего перечисляет методы клиента (`Object.keys(client)`) и прогоняет каждую строку через её парсер — метод без строки краснит тест, поэтому задача, добавляющая метод `BackendClient` в `apps/web` или `apps/bot`, добавляет строку; таблица — по именованным допущениям в байтах (`ASSUMED_*`), строка `readBotTexts` — без запаса `/ 4`. Не ловится: новый fetch-клиент с `response.json()`/`.text()`/`getReader()`/`arrayBuffer()` — ESLint-правила нет (stated); вне правила намеренно: `apps/backend/src/cli/rate-limit-probe.ts` (тело отменяется непрочитанным) и скрипт Mini App `apps/web/src/oauth/client.ts` (браузер). Дедлайн, не зависящий от того, соблюдает ли `fetch` свой abort (#481): REST брокера, OAuth брокера и токен worker'а ограничивают весь вызов (fetch, тело ошибки, `readBody`, разбор) через `withinDeadline` (`packages/shared/src/fetch-deadline.ts`) в свой `timeoutMs`; вызов, не завершившийся через тик после abort, брошен — вызывающий получает код таймаута или отмены, клиент пишет `error` `… request abandoned`, `abandonedFetches()` считает такие вызовы (`fetch-deadline.test.ts`, `rest.test.ts`, `oauth-client.test.ts`, `access-token.test.ts` → «a fetch that ignores its abort signal»); у остальных клиентов правила дедлайн stated, не enforced.

### Rule 51
51. **Отметки против `created_at` (#149, #158, `packages/db/src/schema/columns.ts` → `statementNow`, docs/staff-login.md → «Every update of a column a CHECK orders…»).** Колонка, которую CHECK упорядочивает относительно `created_at` той же строки (`oauth_states.used_at`; `staff_login_challenges.confirmed_at`/`prompt_sent_at`/`code_sent_at`; `staff_login_links.used_at`; `staff_sessions.last_seen_at`/`revoked_at`), в любом UPDATE пишется только `statementNow()` (`clock_timestamp()`), никогда `now()`/`statement_timestamp()`/`new Date()`: `clock_timestamp()` вычисляет сам UPDATE после своего снапшота, `created_at` — всегда `now()` вставившей транзакции (явно не задаётся и не обновляется — stated) и не меняется при перечитывании версии после ожидания, поэтому у любой затронутой строки `created_at` < отметки. INSERT-default (`last_seen_at` новой сессии) и `expires_at` (четыре CHECK'а `> created_at`) пишет транзакция, создающая строку, — вне класса. Девять записей в девяти функциях: `markChallengePromptSent`, `confirmChallengeFromTelegram`, `markChallengeCodeSent`, `runAsStaff`, `revokeStaffSession`, `endStaffSession`, `invalidateIssued` (`disableStaffAccount`, `resetStaffPassword`, `applyStaffPasswordChange`), `consumeOAuthState`, `completeLinkLogin`. Предикаты живости (`expires_at > now()`, окно `last_seen_at`) остаются на `now()`. Touch `runAsStaff` — первый statement своей транзакции только без `lockStaff`; с `lockStaff` `last_seen_at` — момент touch после ожидания строки `staff`; вызывающий, передавший давно открытую `Tx`, сдвигает `last_seen_at` на её возраст. Enforced: `stamp-clock.db.test.ts` — десять строк (девять записей; `invalidateIssued` — под `disableStaffAccount` и `applyStaffPasswordChange`): писатель под транзакцией, открытой до появления строки, `ordered`/`foreknown`/`stamped` — в SQL; `stamp-clock.test.ts` — колонки выводятся из CHECK'ов схемы (пин семи), записи в `packages/*/src`, `apps/*/src` (кроме тестов) и `packages/db/drizzle/*.sql` находятся двумя regex'ами (ключ объекта `.set()`, присваивание в SQL-тексте), каждая обязана быть `statementNow()` без литерала часов, число записей на колонку — пин. Enforcement `partial`, не видит: значение в переменной или helper'е в объектной форме (`const stamp = …; usedAt: stamp` ловит только пин числа записей), `sql.raw` с переменной, объект `.set()` из другого места, spread/computed key, tuple-форму `set (a, b) = (…)`, многострочное raw-значение, `.defaultNow()`/INSERT-default, raw `INSERT … VALUES`, PL/pgSQL `:=`, ключ в кавычках, запись вне этих каталогов. Ложные срабатывания: одноимённая колонка другой таблицы (`auth_sessions.revoked_at`, без CHECK), `where col = now()` — тест краснеет, человек смотрит. Stated: часы БД не шагают назад между созданием строки и отметкой (README → Test database, #166).

### Rule 52

### Rule 65
