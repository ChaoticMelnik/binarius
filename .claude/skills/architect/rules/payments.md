# Architecture Rules — payments

Платежи и начисления: приглашения, постбэки, касса (widget-сессия и страница), покупка за Stars, правила бонусов. Индекс — `.claude/skills/architect/SKILL.md` → Architecture Rules.

### Rule 34
34. **Приглашения (#115, `packages/db/src/user-ops.ts` → `recordUserStart`, `packages/db/src/referral-ops.ts`, docs/referrals.md).** Приглашённый — только пользователь, чью строку `users` создал этот `/start` (`RETURNING old.id is null` того же upsert'а) с payload `ref_<code>` (`referralCodeOf`; `user-ops.db.test.ts` R1, R3). Одна строка на приглашённого — `referrals_invitee_key` (enforced, `schema.db.test.ts`); самоприглашение — `referrals_not_self_check` (enforced). Код — `referral_codes.code`, `NOT NULL` + `referral_codes_code_check` (8 символов base62) + `referral_codes_code_key` (enforced); создаёт его только `readUserReferral`, не для заблокированного пользователя (`referral-ops.db.test.ts` C1, C3). Обе таблицы вне цепочки Rule 5: запись приглашения — в транзакции `recordUserStart` (stated, docs/referrals.md → Recording). Что строка пригласившего старше строки приглашённого — посылка ацикличности блокировок награды (#116, Rule 5); строка `referrals` не обновляется (stated: писатель — только этот insert). Награда (#116, `grantReferralReward`, docs/referrals.md → The reward) — при каждой активации партнёрского аккаунта приглашённым, включая повторный вход через OAuth по уже подтверждённому аккаунту (`active`/`revoked` → `active`, `referral-reward-ops.db.test.ts` W11, W12), пока у `referral_reward` есть действующая версия и пригласивший не заблокирован, одна на приглашение; `already_rewarded` отвечается до чтения правила; `/invite` показывает `connected` и `tokensEarned` (`referral-ops.db.test.ts` R1–R3); уведомление пригласившему о награде — рассылка `referral_rewarded` (#576, Rule 19).

### Rule 35
35. **Постбэки (#141, docs/postbacks.md → Mechanism).** Роут `GET /postbacks/binodex/:secret` регистрируется только при заданном `POSTBACK_URL_SECRET` (`apps/backend/src/index.ts` → `AppDeps.postbacks`; без него путь отвечает 404 not-found-обработчика — `postbacks/routes.db.test.ts`); секрет — сегмент пути `[A-Za-z0-9_-]{32,100}`, сравнение `secretMatches` (sha256 + `timingSafeEqual`, `auth/internal.ts`), неверный — тот же 404 `not_found`; `exposeHeadRoute: false` — HEAD ничего не пишет (тест). Приём никогда не начисляет: не пишет `token_ledger` и `users`, не шлёт в Telegram и брокеру — единственный писатель `recordPostback` (`packages/db/src/postback-ops.ts`) пишет только `deposit_events` (`status = received`) и `postback_deliveries`. Всё, что прошло секрет, журналируется (`outcome = rejected` с причиной из `PostbackRejectReason`), кроме повтора записанного postback id и 400 на не-плоский query (docs/postbacks.md → The route and its answers); 429 — окно процесса 600/мин, только после секрета (неверный секрет слот не занимает — тест). Ответы роутера Fastify (414, 400) — not-found 404 через `frameworkErrors` в `buildApp`, одинаково при включённом и выключенном роуте (тест). Через прокси отвечает только этот роут (`config.publicThroughProxy`, Rule 13); матчер Caddy — по сырому URI (`{http.request.orig_uri}`, только `GET`), конфиг владельца на хосте — stated (docs/postbacks.md → The Caddy route). `withoutSecrets` маскирует декодированный путь (Rule 9). Один депозит на платёж, одна доставка на id, один бонус на депозит — индексами (Rule 7), не чтением. Атрибуция — по `broker_user_id` при `status <> pending` аккаунта (под `FOR SHARE`), иначе при активации (`attachDepositsToAccount`), FK `deposit_events_account_trader_fk` (Rule 4; docs/postbacks.md → Attribution). Расхождение суммы или трейдера у `repeated` — поле `mismatch` результата, `warn` пишет роут только именами полей (тест по логу). Миграция 0044 начинается с guard'а на пустую `deposit_events` (`postbacks-migration.db.test.ts` G1–G2). Столбцы исхода перехода в real (#686, Rule 36): `deposit_events.mode_switch` (`text` + `deposit_events_mode_switch_check` из `DepositModeSwitch`) и `mode_switch_at` (`deposit_events_mode_switch_pair_check`: оба NULL или оба заданы; `schema.db.test.ts`); писатели — только `markDepositModeSwitch` (CAS `mode_switch is null`, проход) и `markUserDepositModeSwitches` (`superseded` из `setTradingMode`), `packages/db/src/deposit-mode-switch-ops.ts`; `recordPostback` и `attachDepositsToAccount` их не пишут, `status`/`processed_at` (#386) переход не пишет; миграция 0075 ставит `predates` каждой строке, бывшей до неё (`deposit-mode-switch-migration.db.test.ts` B1–B4); очередь прохода — частичный индекс `deposit_events_mode_switch_pending_idx`.

### Rule 37
37. **Касса: widget-сессия (#11, docs/deposit.md → The route).** `POST /deposit/widget-session` публичный по `initData`, как OAuth-callback: без bearer, не `publicThroughProxy` — запрос через прокси получает 404 (`postbacks/routes.db.test.ts` G1, `deposit/routes.db.test.ts` D13). Порядок: потолок роута до разбора тела → strict-схема → DEMO_ONLY (Rule 33) → `initData` → окно на пользователя → `resolveBalanceAccount` (`trading_mode` не читается) → `ensureFreshAccessToken(mayRefresh: true)` → один вызов брокера под `DEPOSIT_BROKER_CALL_BUDGET_MS` (D1–D5, D8, D10–D11). Ответ собирается по полям (Rule 9): `{ session, expiresInSec, widgetUrl, widgetOrigin }`, `region` наружу не идёт; `widgetUrl` без `widget_url` брокера строится через `URL` из origin `BROKER_OAUTH_AUTHORIZE_URL` и `BROKER_CLIENT_ID`; origin `widgetUrl` и `widgetOrigin` — только https из `DEPOSIT_WIDGET_ORIGINS`, иначе 502 `broker_rejected` (D6, D7). Каждый источник отказа — своя строка таблицы ошибок `docs/deposit.md` и свой тест. Сессия не логируется: ни одна строка роута, ядра и `deposit-probe` её не пишет, ключ `session` редактируется на любой глубине (`LOG_REDACT_PATHS`; D9 и P1 читают лог и вывод). `deposit-probe` — то же ядро `mintDepositWidgetSession`, `mayRefresh: false`, печатает поля брокера только по origin (P1–P4). `frame-src` страницы и проверка ответа в `web` читают ту же переменную тем же парсером (`parseDepositWidgetOriginsEnv`, compose-пины обоих сервисов) — #111. `POST /deposit/credited` (#112, docs/deposit.md → After a deposit) — в том же плагине, тот же публичный режим; событие виджета — триггер, не данные: строгое тело `{ initData }` (лишний ключ, в том числе сумма, — 400, K6), порядок: тело → DEMO_ONLY до любого чтения (K1) → `initData` (K2) → окно 3/мин на пользователя после `initData` (K3) → `resolveBalanceAccount` (K4) → `touchBalanceRequested` → `balance.refresh(…, { requested: true, mayRefresh: true })` под `DEPOSIT_CREDITED_REFRESH_BUDGET_MS` (K5, K8); исход — таблица `CREDITED_ANSWERS` `satisfies Record<BalanceRefreshOutcome, …>` (K7), строка таблицы ошибок — свой тест; push `sendDepositCredited` — только после `ok`, баланс из записанного снимка, не из запроса (K5/K12), не чаще раза в 60 с на пользователя (окно не возвращается, K9), сбой отправки логируется именем и кодом и ответа не меняет (K10).

### Rule 38
38. **Касса: страница (#111, #112, docs/deposit.md → The page).** `apps/web/src/cashier/`. Скрипт вешает `message`-слушатель до `src` (C13); первое выражение обработчика — фильтр `event.source === iframe.contentWindow && event.origin === widgetOrigin`, затем `data` — объект со строковым `type`, иначе тишина (C1–C3); `init` — только в `widgetOrigin`, никогда `'*'` (C6); сессия загрузки отдаётся первому `ready` моложе `min(45 с, expiresInSec)` и гасится, каждый следующий `ready` — свежий mint (C4–C5); провал свежего mint — его состояние, без `postMessage` (C14). Страница не строит URL: `widgetUrl`/`widgetOrigin` — от backend, `web` перепроверяет оба по своему `DEPOSIT_WIDGET_ORIGINS` (W9). Сессия — ни в URL, ни в storage (C12), ни в логе (W8). CSP — `miniAppCsp(DEPOSIT_WIDGET_ORIGINS)` (`apps/web/src/mini-app.ts`), `frame-src` ровно из списка, без wildcard (W2). `web` — `trustProxy: 'loopback, uniquelocal'`, не число хопов и не `true` (W4, W11); `clientIp` — только через доверенный прокси; окно 60/мин на IP (IPv6 — /64) в `onRequest` роута до разбора тела, до форварда (W6). Каждое состояние страницы — своя строка таблицы `docs/deposit.md` и свой тест (W5, C11), без catch-all по тексту. События виджета (#112): `reauth-required` — свежая сессия в тот же фрейм без перезагрузки, сессия загрузки сбрасывается (C18); `credited` — заметка и POST только `{ initData }`, полезная нагрузка события не читается, ответ POST ничего не меняет (C15, C16); `error` — фиксированная заметка, `message` не читается и не выводится, скрипт не пишет `textContent`/`innerHTML` (C17). Порядок результатов mint'а — результат старого поколения загрузки отбрасывается, свежий mint в полёте один, `unavailable` повторяется один раз, другие состояния — нет (C19, C20, C21a–c, C22). `POST /cashier/credited` берёт тот же объект окна на IP, что и `POST /cashier/session` (W14), форвардит `{ initData }` без `clientIp` и bearer (W12), отвечает 204 при любом исходе форварда (W15). Stated: навигации самого виджета под `frame-src` и поведение под `strict-origin` в webview Telegram — проверка владельца. Высота фрейма (#671): пока виджет на экране, `iframe.style.height` = видимая высота минус всё над фреймом, не меньше `HEIGHT_MIN`; `binodex-embed:resize` высоту не меняет (`client.test.ts` H1–H12); `expand()`, fullscreen и `disableVerticalSwipes()` не вызываются (#671); прокрутка формы внутри фрейма и клавиатура на телефоне — stated (проверка владельца).

### Rule 39
39. **Покупка токенов за Stars (#117, docs/stars.md → The credit).** Пакеты — `STAR_PACKAGES` (`packages/shared/src/stars.ts`), цена и токены замораживаются в строке `star_payments`. Единственный писатель, вставляющий строки `star_payments` и строки покупки Stars в леджер, — `creditStarPayment` (`packages/db/src/star-payment-ops.ts`): проваленная проверка — статус `held`, без строки леджера. Каждая строка хранит плательщика `payer_telegram_user_id` (#118). Payload `stars:<code>:<users.id>` разбирает один `parseStarsInvoicePayload`. Pre-checkout только читает и никогда не отвечает `ok: true` без «да» backend'а (`stars.test.ts`). Потерянный `successful_payment` закрывает сверка `star-reconciler.ts` (docs/stars.md → Reconciliation): неизвестный charge → тот же `creditStarPayment`, начисление сверки — push «⭐ Начислено …» (`star-reconciler.db.test.ts` S3, S11). Вход в покупку — только при активном аккаунте (`stars.test.ts` S7). Возврат (#118, docs/stars.md → Refunds) — только через сотрудника: `stars refund <charge id> --reason` (`apps/backend/src/cli/stars.ts`) вызывает `refundStarPayment` плательщику без открытой транзакции и пишет `recordStarRefund` только по `true` или по 400 с `CHARGE_ALREADY_REFUNDED`; любой другой ответ и таймаут ничего не пишут (`stars.db.test.ts` C1–C6); `GrammyError` 5xx — исход неизвестен, не отказ (#626 п.3, #510: `classifyRefundAnswer` в `apps/backend/src/payments/star-refund.ts`, один разбор ответа для CLI и админки, `star-refund.test.ts` T1–T6, `stars.db.test.ts` C10). Из админки (#510) — `POST /admin/star-payments/:id/refund` проверяет тело до сессии (SR3), сессию — `readLiveStaffContext` (SR1), вызывает `refundStarPayment` плательщику (SR6) под `withinDeadline(STARS_REFUND_BUDGET_MS)` без транзакции и пишет `recordStarRefundByStaff` только по `true` или `CHARGE_ALREADY_REFUNDED` (SR2, SR5); отказ и неизвестный исход — только строка аудита (SR10, SR11); уже `refunded` — без Telegram (SR4); строка — от сотрудника, проверенного до вызова (SR9). Заявки `/paysupport` — один запрос `listOpenStarRefundRequests` для `stars requests` (50) и страницы админки (keyset, `star-payment-ops.db.test.ts` Q1–Q4, `admin/routes.db.test.ts` SR8). `held` возвращается без списания токенов. Сверка записывает исходящую транзакцию пользователю с id известного `paid`/`held` charge тем же писателем, получатель — плательщик, `transaction_type` не сужается (`star-reconciler.db.test.ts` S20–S26). `/paysupport` — список и заявка, уведомление сотрудникам после коммита; `ps:r:` — запись, без «Повторить» (`paysupport.test.ts`).

### Rule 40
40. **Правила бонусов (#13, docs/bonus-rules.md → The model; docs/referrals.md → The reward).** Каждое начисление `bonus` — по версии правила: `bonus_rules` (`code`, `version` от 1, `kind` из `BonusRuleKind` — CHECK `bonus_rules_kind_check`, `params`); строка неизменяема (Rule 3), изменение — новая версия. Одна действующая версия на код — `bonus_rules_active_code_idx` (частичный unique `where is_active`); новая версия вставляется неактивной (default `false`). Разрешение — `resolveActiveRule`: действующая версия с окном `valid_from`/`valid_to` по `now()` транзакции (часы БД). Параметры разбираются при чтении схемой вида (`packages/shared/src/bonus.ts`); не разобрались или вид не тот, что нужен ссылке, — `InvalidBonusRule` (имя и код правила, Rule 8), транзакция вызывающего откатывается, суммы по умолчанию нет. Нет действующей версии — `{ granted: false, reason: 'no_active_rule' }`, без начисления. Ссылка `applyBonus` — `{ brokerAccountId }` (вид `link_bonus`) или `{ referralId }` (вид `referral_reward`); ссылка задаёт и вид версии, и arbiter `ON CONFLICT` (`bonus-rule-ops.db.test.ts` → a reference the rule kind does not take). Единственный писатель строк `bonus` — `applyBonus` (Rule 2); строка называет версию (`bonus_rule_id` + `bonus_rule_kind`, Rule 4), вид версии закреплён по ссылке `token_ledger_bonus_rule_check` (enforced). Единственный писатель `bonus_rules`, кроме сида 0059, — CLI `bonus-rule` (`apps/backend/src/cli/bonus-rule.ts`, docs/bonus-rules.md → The CLI); SQL руками его обходит (stated), но не триггеры.
